# Part I - Initiative Report

## HAAG Project Snapshot + Starter Path

## Describe your initiative / procedure

My initiative is a lightweight onboarding and project-clarity procedure for HAAG. The main idea is that each project should maintain a simple, up-to-date "first stop" for newcomers and potential contributors. Right now, project information is often spread across Slack threads, GitHub repos, documents, webpages, and older materials. Because of this, it can be hard for someone new to understand what a project is doing, what the current goal is, who owns what, and how to get started. To address that problem, the initiative proposes two simple artifacts for each project:

- **Project Snapshot** — a short one-page overview of the project.
- **Demo Log** — a lightweight running log of meaningful project updates.

The Project Snapshot is meant to answer the most basic questions quickly:

- What is this project?
- What problem is it solving?
- What is the current goal this month or this semester?
- What is the current status?
- Who are the main contacts?
- What are the most important links?
- How can a newcomer start contributing?

The Demo Log is meant to capture progress in a simple way over time. It can include a short note on what changed, why it matters, a link to the relevant artifact, and the next step or open question. The procedure is designed to be asynchronous and low-overhead. Rather than relying on a live event or a long onboarding conversation every time someone joins, the project can point newcomers to one clear starting place. The intent is to reduce onboarding friction, improve project visibility, and make it easier for people to contribute.

At this stage, I see the initiative as an organizational experiment in the discovery-to-pilot stage rather than a fully implemented system. My goal for this semester is to define the procedure clearly, identify a realistic way to test it, and move toward a small pilot.

## Explain the hypotheses / KPIs you have measured at this time and what is left to be measured

The main hypothesis behind this initiative is: If HAAG projects provide a simple, standardized Project Snapshot and Demo Log, then newcomers and potential contributors will understand project context faster, ask fewer repeated onboarding questions, and feel more confident about how to begin. A second related hypothesis is: If project context is easier to find and more current, then project teams will spend less time repeating the same introductory information and more time on actual project work.

### KPIs identified so far

- **Clarity score** — a self-reported score, such as 1-5, on whether a person understands what the project is doing and how to contribute.
- **Time-to-context** — how long it takes a newcomer to find enough information to understand where to start.
- **Repeated onboarding questions** — how often project leads or managers receive the same introductory questions such as "Where is the repo?", "Who should I talk to?", or "How do I get started?"
- **Starter-task readiness** — whether a newcomer can identify at least one reasonable next step after reviewing the snapshot.

### What has been measured so far

I am still in an early phase, so I would describe these as identified KPIs rather than fully measured outcomes. So far, I have mainly done problem definition and selected the indicators I believe are realistic and useful. I have not yet run a full before-and-after pilot with enough data to claim improvement.

### What is left to be measured

- Collecting a small baseline from current onboarding experiences.
- Piloting the snapshot with one project or team.
- Gathering quick user feedback.
- Comparing the before-and-after experience using the KPIs above.

I would especially like to validate whether the initiative actually lowers confusion and shortens the time it takes for someone new to get oriented.

## Explain your method for testing these hypotheses

My testing approach is a small pilot rather than a large rollout. The idea is to start with one willing project, create the Snapshot and Demo Log, and then ask a small number of users to interact with them and give feedback.

### Narrative testing method

1. Identify where current project context is scattered.
2. Draft a Project Snapshot and Demo Log template.
3. Fill in the template for one pilot project.
4. Ask a small group of newcomers or potential contributors to review it.
5. Ask them a few quick questions about clarity, contacts, and how to begin.
6. Compare their experience to the current status quo.
7. Revise the procedure based on what was confusing or missing.

### Simple flow

Current scattered onboarding experience -> template creation -> pilot with one project -> small user review -> feedback collection -> revision -> possible broader use.

## Explain how stakeholders are engaging with your initiative

The stakeholders for this initiative include project leads, project managers or co-managers, newcomers, current researchers, and HAAG leadership. Each group is connected to the problem in a different way.

- **Newcomers and potential contributors** are the primary audience because they experience the onboarding confusion most directly.
- **Project leads and managers** are important because they are often the ones repeatedly answering introductory questions or pointing people to resources.
- **HAAG leadership** may care about the initiative because it creates more visibility and standardization across projects.

At this stage, stakeholder engagement has been more indirect than formal. My understanding of the problem has come mainly from observing how project information is currently spread out and from thinking through the repeated friction points that occur when people need project context quickly. That means engagement has not yet reached the level of a formal pilot with committed participants. This does not fully match an ideal expectation. In an ideal case, I would already have a small pilot project and a few stakeholder responses. Instead, the initiative is still at the stage of refining the procedure and clarifying the smallest useful version of the experiment.

Given that reality, the main change I think is necessary is to keep the scope extremely small. Rather than trying to get many projects involved, the next step should be to find one willing team and test the simplest version of the procedure. I also think the framing should emphasize that this is intended to reduce overhead, not create extra bureaucracy.

## What processes have you documented or begun documenting to ensure sustainability?

The main sustainability idea for this initiative is to make the procedure simple enough that teams can realistically keep it current. So far, I have begun documenting the following:

- the problem statement,
- the purpose of the Project Snapshot,
- the purpose of the Demo Log,
- the suggested content for each artifact,
- the idea of adding a Last Updated date,
- and the idea of assigning a primary owner and a backup owner.

My current plan is for the procedure to be hosted in a GitHub repo or wiki-based location where teams can easily link to it and update it asynchronously. A likely structure would be:

- `PROJECT_SNAPSHOT.md`
- `DEMO_LOG.md` or a `demos/` folder
- a simple index page that links to the latest project snapshot

### Additional documentation I plan to complete

## How are you currently measuring progress toward your goals?

At this point, I am measuring progress more by design progress and pilot readiness than by final outcome data. The main indicators of progress so far are:

- I narrowed the initiative from a broader collaboration idea to a more realistic onboarding / project-clarity idea.
- I clearly defined the problem the initiative is trying to solve.
- I identified a small set of realistic KPIs.
- I outlined what the core artifacts should be.
- I identified a small pilot strategy rather than an overly broad rollout.

The main success indicators I am looking for are whether the initiative becomes simple enough to test, useful enough to reduce confusion, and lightweight enough that a real team would be willing to adopt it. The main challenge indicators are the opposite: if the materials become too long, too burdensome, or too hard to keep current, then the initiative will lose value.

## Describe any obstacles or bottlenecks that have arisen

One bottleneck has been scope. I originally considered a broader collaboration-style initiative, but that version included too many moving parts and would have been harder to test in a limited amount of time. Narrowing the initiative to onboarding and project clarity made it much more realistic. Another bottleneck has been the difference between a good idea in theory and a manageable experiment in practice. It is easy to describe a helpful system, but harder to define the smallest version that a real team would be willing to try.

### Anticipated challenges that have materialized

- Information staleness is a real risk.
- Adoption friction is likely if the procedure feels too long or too formal.
- Limited stakeholder bandwidth makes it harder to move quickly from concept to pilot.

### Unexpected issues

One issue that became clearer than expected is that the initiative needs to be positioned very carefully. If it is framed as a large system or as another organizational requirement, it may feel burdensome. If it is framed as a lightweight first stop that reduces repeated questions, it becomes more attractive and easier to justify. A second issue is that, under time pressure, it is tempting to keep revising the initiative concept rather than move forward with one version. For that reason, I have decided that the most useful next step is to commit to the current onboarding and project-clarity version and treat this mid-semester report as part of solidifying that direction.
